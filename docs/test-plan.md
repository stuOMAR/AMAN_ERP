# AMAN ERP - خطة اختبارات Playwright E2E

## نظرة عامة

هذه الخطة تغطي اختبارات End-to-End عبر API باستخدام Playwright. الاختبارات تتحقق من:
1. تعبئة البيانات الرئيسية (Seed)
2. المصادقة والصلاحيات
3. عزل الفروع والعملات
4. المعاملات المالية
5. المخزون والمنتجات
6. الموارد البشرية

## البيئة المطلوبة

- Backend يعمل على `http://localhost:8000`
- قاعدة بيانات اختبار منفصلة (tenant DB)
- مستخدم admin_system كلمة المرور: `admin123`
- company_code للاختبار

## هيكل الاختبارات

```
tests/
├── playwright.config.ts
├── fixtures/
│   ├── api-client.ts          # أدوات API مساعدة
│   └── scenarios.ts           # بيانات السيناريوهات
├── seed/
│   └── seed.spec.ts           # تعبئة البيانات الرئيسية
└── specs/
    ├── auth.spec.ts            # المصادقة
    ├── branches.spec.ts        # الفروع
    ├── currencies.spec.ts      # العملات وأسعار الصرف
    ├── permissions.spec.ts     # عزل الصلاحيات
    ├── financial.spec.ts       # المعاملات المالية
    ├── inventory.spec.ts       # المخزون والمنتجات
    ├── hr.spec.ts              # الموارد البشرية
    └── isolation.spec.ts       # عزل الفروع الشامل
```

## Phase 1: Seed (تعبئة البيانات)

### TC-SEED-001: إنشاء الشركة والـ tenant database
- **الهدف**: إنشاء شركة جديدة عبر API والتحقق من إنشاء قاعدة البيانات
- **الخطوات**:
  1. `POST /api/companies/` ببيانات الخليج القابضة
  2. التحقق من إرجاع `company_id`
  3. التحقق من إمكانية تسجيل الدخول بالـ admin credentials
- **التحقق**: `company_id` موجود، login يُرجع `access_token`

### TC-SEED-002: تعبئة العملات وأسعار الصرف
- **الهدف**: إنشاء 4 عملات مع أسعار صرف
- **الخطوات**:
  1. إنشاء SAR (base=true, rate=1)
  2. إنشاء EGP, AED, USD (base=false, rates مختلفة)
  3. إنشاء exchange rates لكل عملة
- **التحقق**: `GET /api/currencies/` يُرجع 4 عملات، SAR.is_base=true

### TC-SEED-003: تعبئة الفروع
- **الهدف**: إنشاء 3 فروع بعملات مختلفة
- **الخطوات**:
  1. إنشاء الرياض (SAR, is_default=true)
  2. إنشاء القاهرة (EGP)
  3. إنشاء دبي (AED)
- **التحقق**: `GET /api/branches/` يُرجع 3 فروع، كل فرع له `default_currency` صحيحة

### TC-SEED-004: تعبئةدليل الحسابات والخزائن
- **الهدف**: إنشاء شجرة حسابات وخزائن مرتبطة بالفروع
- **الخطوات**:
  1. إنشاء الحسابات (أصول، التزامات، إيرادات، مصروفات)
  2. إنشاء خزائن لكل فرع بعملتها
- **التحقق**: كل خزينة مرتبطة بفرع وعملة وحساب GL

### TC-SEED-005: تعبئة الموظفين والمستخدمين
- **الهدف**: إنشاء موظفين مع مستخدمين بأدوار مختلفة
- **الخطوات**:
  1. إنشاء إدارات ومسميات وظيفية
  2. إنشاء 6 موظفين (CEO, مدير مالي, مدير فرع مصر, مدير فرع دبي, كاشير, مراجع)
  3. كل موظف ينشئ مستخدم تلقائياً
- **التحقق**: `GET /api/hr/employees/` يُرجع 6 موظفين، كل مستخدم يستطيع login

### TC-SEED-006: تعبئة المنتجات والعملاء
- **الهدف**: إنشاء منتجات وعملاء وموردين
- **الخطوات**:
  1. إنشاء تصنيفات ووحدات
  2. إنشاء 3 منتجات (2 سلع + 1 خدمة)
  3. إنشاء 3 عملاء + 1 مورد
  4. إنشاء قوائم أسعار لكل عملة
- **التحقق**: المنتجات والعملاء موجودين مع الأسعار الصحيحة

## Phase 2: Auth & Security (المصادقة والأمان)

### TC-AUTH-001: تسجيل الدخول الناجح
- **الهدف**: التحقق من تسجيل الدخول وإرجاع token
- **前置**: مستخدم موجود من seed
- **الخطوات**:
  1. `POST /api/auth/login` ببيانات صحيحة
  2. التحقق من إرجاع `access_token`, `refresh_token`, `company_id`
- **التحقق**: status=200, token صالح

### TC-AUTH-002: تسجيل الدخول بكلمة مرور خاطئة
- **الهدف**: التحقق من رفض كلمة المرور الخاطئة
- **الخطوات**:
  1. `POST /api/auth/login` بكلمة مرور خاطئة
  2. التحقق من إرجاع 401
- **التحقق**: status=401, لا يوجد token

### TC-AUTH-003: Rate limiting على تسجيل الدخول
- **الهدف**: التحقق من قفل الحساب بعد محاولات فاشلة متكررة
- **الخطوات**:
  1. إرسال 5 محاولات فاشلة متتالية
  2. محاولة سادسة يجب أن تُرفض
- **التحقق**: status=429 بعد الحد المسموح

### TC-AUTH-004: الوصول بدون token
- **الهدف**: التحقق من رفض الطلبات بدون مصادقة
- **الخطوات**:
  1. `GET /api/auth/me` بدون Authorization header
- **التحقق**: status=401

### TC-AUTH-005: الوصول بـ token منتهي الصلاحية
- **الهدف**: التحقق من رفض token قديم
- **الخطوات**:
  1. استخدام token مزيف/منتهي
  2. `GET /api/auth/me`
- **التحقق**: status=401

### TC-AUTH-006: تحديث Token (Refresh)
- **الهدف**: التحقق من تجديد token عبر refresh token
- **الخطوات**:
  1. تسجيل الدخول والحصول على refresh_token
  2. `POST /api/auth/refresh` بالـ refresh_token
  3. التحقق من إرجاع access_token جديد
- **التحقق**: token جديد مختلف عن القديم

## Phase 3: Branches & Currencies (الفروع والعملات)

### TC-BR-001: قائمة الفروع حسب الصلاحية
- **الهدف**: CEO يرى كل الفروع، مدير الفرع يرى فرعه فقط
- **前置**: مستخدمين بصلاحيات مختلفة
- **الخطوات**:
  1. Login كـ CEO → `GET /api/branches/` → يُرجع 3 فروع
  2. Login كـ مدير فرع القاهرة → `GET /api/branches/` → يُرجع فرع واحد
- **التحقق**: عدد الفروع يتطابق مع الصلاحيات

### TC-BR-002: منع تكرار branch_code
- **الهدف**: التحقق من فريدية كود الفرع
- **الخطوات**:
  1. محاولة إنشاء فرع بـ branch_code مكرر
- **التحقق**: status=400 أو 409

### TC-BR-003: الفرع الافتراضي
- **الهدف**: التحقق من وجود فرع افتراضي واحد فقط
- **الخطوات**:
  1. التحقق أن الرياض is_default=true
  2. محاولة تعيين فرع آخر كافتراضي
- **التحقق**: الفرع القديم يصبح is_default=false

### TC-CUR-001: عملة التقارير الأساسية
- **الهدف**: التحقق من عملة واحدة فقط is_base=true
- **前置**: SAR.is_base=true
- **الخطوات**:
  1. `GET /api/currencies/` → SAR.is_base=true, الباقي false
  2. محاولة تعيين عملة أخرى is_base=true
- **التحقق**: SAR تبقى هي الأساسية أو يتم التبديل

### TC-CUR-002: أسعار الصرف
- **الهدف**: التحقق من صحة أسعار الصرف
- **前置**: exchange rates موجودة
- **الخطوات**:
  1. `GET /api/currencies/` → التحقق من rates
  2. حساب: 1000 AED × 1.021 = 1021 SAR
- **التحقق**: الأسعار متطابقة مع المُدخلة

### TC-CUR-003: تحديث سعر الصرف
- **الهدف**: التحقق من إمكانية تحديث سعر الصرف
- **الخطوات**:
  1. تحديث سعر EGP من 0.076 إلى 0.080
  2. التحقق من التحديث
- **التحقق**: السعر الجديد مُطبق

## Phase 4: Permissions (عزل الصلاحيات)

### TC-PERM-001: صلاحيات الدور
- **الهدف**: التحقق من أن كل دور لديه الصلاحيات المحددة
- **前置**: مستخدمين بأدوار مختلفة
- **الخطوات**:
  1. `GET /api/roles/permissions` → قائمة كل الصلاحيات
  2. التحقق من أن CEO لديه `dashboard.executive`
  3. التحقق من أن cashier لا يملك `accounting.manage`
- **التحقق**: الصلاحيات متطابقة مع ROLE_PERMISSIONS

### TC-PERM-002: رفض الوصول بدون صلاحية
- **الهدف**: التحقق من رفض الوصول للموارد بدون صلاحية
- **前置**: مستخدم cashier (صلاحيات محدودة)
- **الخطوات**:
  1. Login كـ cashier
  2. محاولة `POST /api/accounting/journal-entries` → يجب رفضه
  3. محاولة `DELETE /api/inventory/products/{id}` → يجب رفضه
- **التحقق**: status=403 لكل محاولة

### TC-PERM-003: صلاحيات الحقول (Field-level)
- **الهدف**: التحقق من إخفاء الحقول الحساسة حسب الدور
- **前置**: مستخدم بدون `hr.pii` permission
- **الخطوات**:
  1. `GET /api/hr/employees/{id}` كمستخدم عادي
  2. التحقق من إخفاء salary, bank_account, national_id
- **التحقق**: الحقول الحساسة = null أو مخفية

### TC-PERM-004: Wildcard صلاحيات
- **الهدف**: التحقق من أن `*` تعطي كل الصلاحيات
- **前置**: مستخدم admin أو superuser
- **الخطوات**:
  1. Login كـ admin
  2. محاولة الوصول لأي endpoint محمي
- **التحقق**: status=200 لكل endpoint

## Phase 5: Financial Transactions (المعاملات المالية)

### TC-FIN-001: إنشاء فاتورة مبيعات
- **الهدف**: إنشاء فاتورة مبيعات مع ضريبة
- **前置**: عميل ومنتج موجودين من seed
- **الخطوات**:
  1. `POST /api/sales/invoices` بفاتورة للعميل الرياض
  2. سطر: 10 × tablet @ 1200 SAR + 15% VAT
  3. التحقق من المجموع: 12000 + 1800 = 13800 SAR
- **التحقق**: الفاتورة created، المجموع صحيح، القيود المحاسبية متوازنة

### TC-FIN-002: قيد محاسبي متوازن
- **الهدف**: التحقق من توازن القيود المحاسبية
- **前置**: فاتورة مبيعات موجودة
- **الخطوات**:
  1. جلب القيود المرتبطة بالفاتورة
  2. التحقق: مجموع المدين = مجموع الدائن
- **التحقق**: debit_total == credit_total

### TC-FIN-003: فاتورة بعملة مختلفة
- **الهدف**: إنشاء فاتورة بعملة غير عملة التقارير
- **前置**: عميل دبي (AED)
- **الخطوات**:
  1. إنشاء فاتورة بالـ AED
  2. التحقق من تحويلها لـ SAR بالسعر 1.021
- **التحقق**: المبلغ بالـ SAR = المبلغ AED × 1.021

### TC-FIN-004: سند قبض
- **الهدف**: تسجيل سند قبض لفاتورة
- **前置**: فاتورة مبيعات غير مدفوعة
- **الخطوات**:
  1. `POST /api/finance/payments` بسند قبض
  2. ربط السند بالفاتورة
  3. التحقق من تحديث رصيد الخزينة
- **التحقق**: الخزينة زادت، الفاتورة مدفوعة

### TC-FIN-005: إنشاء خزينة بعملة الفرع
- **الهدف**: التحقق من تطابق عملة الخزينة مع الفرع
- **前置**: فرع القاهرة (EGP)
- **الخطوات**:
  1. محاولة إنشاء خزينة بالـ SAR في فرع القاهرة
  2. يجب أن تُرفض أو تُقبل حسب السياسة
- **التحقق**: السلوك المُتوقع

- **التحقق**: الأسعار متطابقة مع المُدخلة

## Phase 8: Cross-Branch Isolation (عزل الفروع الشامل)

### TC-ISO-001: عزل الفواتير بين الفروع
- **الهدف**: مدير فرع لا يرى فواتير فروع أخرى
- **前置**: فاتورة في الرياض + فاتورة في القاهرة
- **الخطوات**:
  1. Login كمدير الرياض
  2. `GET /api/sales/invoices` → فواتير الرياض فقط
  3. Login كمدير القاهرة
  4. `GET /api/sales/invoices` → فواتير القاهرة فقط
- **التحقق**: كل مدير يرى فواتير فرعه فقط

### TC-ISO-002: عزل الخزائن بين الفروع
- **الهدف**: لا يمكن الوصول لخزينة فرع آخر
- **前置**: خزائن لكل فرع
- **الخطوات**:
  1. Login كمدير الرياض
  2. محاولة إنشاء سند صرف على خزينة دبي → 403
- **التحقق**: status=403

### TC-ISO-003: عزل المخزون بين الفروع
- **الهدف**: كل فرع يرى مخزونه فقط
- **前置**: مخزون في مستودعين مختلفين
- **الخطوات**:
  1. Login كأمين مستودع الرياض
  2. `GET /api/inventory/` → مخزون الرياض فقط
  3. محاولة تعديل مخزون دبي → 403
- **التحقق**: الوصول محدود

### TC-ISO-004: CEO يرى كل الفروع
- **الهدف**: التحقق من وصول CEO لكل شيء
- **前置**: CEO بـ allowed_branches = كل الفروع
- **الخطوات**:
  1. Login كـ CEO
  2. `GET /api/branches/` → 3 فروع
  3. `GET /api/sales/invoices` → كل الفواتير
  4. `GET /api/hr/employees/` → كل الموظفين
- **التحقق**: CEO يرى كل شيء

### TC-ISO-005: Auditor read-only access
- **الهدف**: التحقق من أن المراجع لا يمكنه التعديل
- **前置**: auditor role
- **الخطوات**:
  1. Login كـ auditor
  2. `GET /api/sales/invoices` → 200 (قراءة)
  3. `POST /api/sales/invoices` → 403 (منع كتابة)
  4. `DELETE /api/inventory/products/{id}` → 403 (منع حذف)
- **التحقق**: read OK, write/delete = 403
